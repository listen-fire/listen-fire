Affinity is listened to on a record's `Changes` (``listen to crm-[:`List Entry — Master Deals List`]->-[c:Changes WHERE c.Field == "Status"]-> fire f``, ``function f(c: <crm-[:`List Entry Change — Master Deals List`]->>)``): an organization's, a person's, an opportunity's and each list's entries', each their own record type (`OrganizationChange`, `PersonChange`, `OpportunityChange`, `List Entry Change — <list>`) with `Kind` (`created`, `updated`, `deleted`) and, when a field's value was set or cleared, `Field`, the field's name as its record shows it (an enum of the record's own fields). A webhook delivery is the arrival on the changed record's `Changes`, carrying the record as Affinity holds it now, `about` it and `occurredAt`; a redelivery of the same change runs nothing. One webhook per connection serves every listen on `Changes` (`ensureEventSubscription({ edge: "Changes" })`). A run can wait on a record's next change: `awaitKeys` keys it by the kind of record and its id (`organization:13`), as each arrival is keyed, since Affinity numbers organizations, persons, opportunities and list entries apart; it needs the head's `recordType`, which a 2.6 host names. It declares how a 0.12 `listen to crm { events: [...] }` naming an organization's, a person's or an opportunity's events becomes a listen on its `Changes` (`listenSettingsBecome`); one naming a list entry's, a field value's, a note's or a reminder's event, or none, has no rewrite. Adapter protocol 2.6. `subscribableEvents` is gone, and notes and reminders no longer run anything.
