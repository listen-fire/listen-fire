# @listen-fire/engine

## 0.12.11

### Patch Changes

- fb8ee71: `lf runs rerun <run-id>` runs a failed run again as the same run's next attempt: with the event (or manual text) it ran on, against the movement as the project holds it now, from the start. `lf runs show` lists every attempt with its status, times, writes and error; the run's status is its latest attempt's. Only a run whose latest attempt failed is rerun: a succeeded, running or parked run is refused by name, so a second rerun after one that succeeded runs nothing. A failed attempt that committed writes before it failed is refused unless `--force`, and the refusal lists those writes. A failed run now keeps the writes it made in its outcome (they used to be dropped when it failed). The store slot adds `runs.rerun`, and a run row may answer `attempt` and `attempts`.

## 0.12.10

### Patch Changes

- 26d988a: An Airtable listen can fire on one field changing, and on it changing to a value: `listen to hiring { base: "app…", table: "tbl…", field: "Stage", becomes: "Interview" } fire …` runs only when a change touched `Stage` and made it `Interview` (it was not `Interview` before). The `Record Change` event names the fields a change touched (`Changed Fields`) and reaches the row as it was through an `Old Record` edge, typed like the table, so `change-[:`Old Record`]->.Stage` is the `Stage` enum. A new Airtable webhook asks for previous cell values; select cells in a delivery read as their choice's name. The engine's listen scope gate (`eventMatchesTriggerScope`) applies `field` over an event's `changedFields` and `becomes` over its payload's `fields` and `previous`.
  
  The checker holds both keys against the table the listen watches. A module declares them with two new listen config formats: `field` (one field of the watched record) and `field-value` (a value of the field the `field` key names, beside exactly one `field` key). A `field` the table lacks is refused, naming the table's fields (`MOV_LISTEN_BAD_CONFIG`); a `becomes` that is not a choice of a select field is refused with a did-you-mean (`MOV_ENUM_UNKNOWN_VALUE`), and one of the wrong type for any other field (text for a number field) is refused (`MOV_LISTEN_BAD_CONFIG`), as is a `becomes` without a `field`. Only configs that could never fire are refused. `lf` applies the same `field` and `becomes` gate as the engine.
  
  A listen config format a checker does not know no longer refuses the catalog. A newer module may declare a format an older core lacks; its key's value is then a plain, unchecked value, and the checker says so once as an Info naming the format (`MOV_LISTEN_BAD_CONFIG`, severity info). `lf`'s manifest reader and the wire schema (`WireListenDeclarations`) keep such a format rather than refusing the manifest. So a module release no longer needs the core released first.
  
  `lf serve` registers Airtable webhooks. A module may declare `subscriptionScopeKeys` in its manifest (`module-kit` states them; Airtable's are `base` and `table`): `lf` then keeps one webhook per credential and scope, the scope being a listen's config values of those keys, and sends it as `scope` on `ensureEventSubscription` and `removeEventSubscription`, as the platform does. Each scoped webhook has its own door, `/api/public/webhook-sync/<provider>/<credential>/<key>` (the key is the scope's values, `appHIRE01.tblCAND01`), its own secret and pull cursor, and is kept in the credential's `webhook_subscriptions` field. A delivery there runs only the listens of that credential and scope; adding or removing a listen on another table registers or removes only that table's webhook. A module that declares no scope keys keeps its one webhook per credential, in the same fields and at the same door as before. A delivery's events are read (`preprocessInbound`, `wakeKeys`) as the user credential its door names, so a pulled source such as Airtable can read its payload feed. The fake Airtable gains a delivery door (`POST /airtable/control/deliver`) that queues a change on every webhook of the base that takes it and pings each one signed as Airtable signs, and its changes may carry previous cell values.
  
  Under `lf`, the event's `Record` and `Old Record` edges are narrowed to the table a movement's signature names, as the platform narrows them: in `function f(change: <hiring-[:`Record Change` WHERE `table` == "tblCAND01"]->>)`, `change-[:`Old Record`]->.Stage` is the Candidates table's `Stage` enum. A listen config key may declare `narrows: { collection, matchField }` (on the wire manifest; `module-kit` states it; Airtable's `base` and `table` do): it is one hop of the address. `lf` walks the address with the module's `edgesFrom` from the connection's root (a connection's entry position consumes the hops it pins), grafts a copy of the event node per address with its edges onto the last hop's collection retargeted at the walked table, and publishes the hop values a listen may name, so a listen's unknown table id is refused with a did-you-mean.
  
  Adapter protocol 2.4: an event subscription a source lets lapse. `ensureEventSubscription` may answer `expiresAt`, and a module may list `refreshEventSubscription` (`{ externalId, scope? }` → `{ expiresAt? }`); `PROTOCOL_MINOR` is 4 in `engine-contracts` and `module-wire` (`lf` and the engine speak 2.0 to 2.4). A module's stated minor is now what it needs its host to speak: its author's declared `protocolMinor`, else 0 — `protocolMinorOf`/`protocol_minor_of`, the module-kit stamping (TypeScript and Rust) and the slot manifests no longer raise it for offered methods, so a module listing `refreshEventSubscription`, a `.watch` or `work.enqueueIfAbsent` states 0 and an older host still reads it; `minorIntroducing`/`minor_introducing` name the minor that introduced a method a host requires. `lf` keeps each webhook's expiry with its registration and queues a `refresh_subscription` work row a day before it (halfway there for a lifetime under two days), which `lf serve` runs on its tick and `lf drain` takes, the wake slot told when it is due. A refresh that fails is printed once and tried again in 15 minutes; a webhook found lapsed is removed, registered anew and its pull cursor reset; one kept with no expiry is refreshed at once to learn it. Airtable answers its webhook's `expirationTime` as `expiresAt` from registering and refreshing, and lists `refreshEventSubscription`. The fake Airtable gains a clock (`POST /airtable/control/advance-clock { ms }`): a webhook past its expiry is pinged no more and cannot be refreshed. A webhook `lf serve` replaces because its events or door changed has its pull cursor reset too.
- d4302ff: A field read off a name bound to a walk reads each record the walk landed on, as the walk read in place does: after `row = change-[:Record]->`, `"${row.Stage}"` is the Stage, where it read as empty (`change-[:Record]->.Stage` already read it). This holds for any walk bound to a name, not only one from the event: a field read off a list of records reads each record's field. A read off a list holding anything else is unchanged.
- 56fb1c7: `lf credential add` for a plugin module (`--module @lf/jev`) prints how a movement calls its plugins (``import { `@lf/jev` as jev } from plugins``) instead of an adapter's `connect … using …`, which does not apply to a plugin.
- 8d4a1e2: The routing rule for an inbound event is public in `public/inbound`, beside `eventMatchesTriggerScope`: `listenHearsCredential(listened, delivered)` (a listen whose construction names a credential hears only that credential's deliveries; a listen that names none, or a delivery addressed to the module's install, hears or reaches every one), and `listenerHearsDelivery(listener, { adapterType, credentialName?, event })`, the whole rule for one listen. It is the rule `lf` and the hosted product route by; a shared table of cases (`packages/engine-contracts/conformance/listen-hears.json`) holds the TypeScript and `lf`'s Rust to it.
- 2a5e666: A describe may mark a field `pinned: true`: a read of that type must pin the field in its `WHERE` with `==` (to a literal or a name in scope, among the `WHERE`'s `AND`-joined conditions, in a `WHERE` that calls no function and tests no `EXISTS`), because the source takes it as an argument of the read. `lf check` refuses a read that does not (`MOV_HOP_PIN_REQUIRED`), naming the fields and the form to write. Both catalog builders carry it as the position's `pinnedProperties`. Writes are unaffected, and no module set the flag before `@lf/mcp` did, so every program that checked before checks the same unless it reads an MCP tool without its required arguments, which failed at run.
- 783d349: `lf` reads a file a module owns (a Gmail attachment, a Drive file) for an extraction or `File.read`: it fetches the bytes through the owning module's `resolveFileRef`, as a write that files the same attachment elsewhere already did, then reads the PDF's text layer (or asks the ocr slot) as for a stored file. Before, the run warned `MOVENG_FILE_BYTES_UNAVAILABLE` ("a file 'gmail' owns is not read by lf yet") and the extraction saw nothing.
- 0215c37: `lf` describes a module once per position a program constructs it with, and sends that position on every call of the connection, so an Airtable base's tables are typed and checked under `lf`. A module's manifest may declare `positionArgs` (`module-kit` states them from the module's manifest); the fake Airtable's Companies table gains select fields with choices. The checker holds each text literal of a list written into a list of enum (an Airtable multiple select) against the enum, and a WHERE written inside a parameter's type (`<crm-[c:Companies WHERE c.Stage == "Lost"]->>`) against the enum of the field it compares, as it already did a single literal and a WHERE in a body (`MOV_ENUM_UNKNOWN_VALUE`). A listen on a positioned connection is polled in its position (the call's `settings`) under a checkpoint of its own.
- a6b6686: A listen can declare what its events are, as a node the program declares: `listen to stripe { payload: <Payment> } fire f`, for a module whose listen-config key has the new catalog format `type` (`@lf/webhook`'s `payload`). The movement it fires is checked against that node field by field, and reads in its body are checked against it. Under `lf`, an event whose payload does not fit the node fires nothing, and a delivery none of whose listens it fits is answered 400 `payload_mismatch`, naming the fields. The engine holds a parameter typed by a declared node as the event's payload, so `e.amount` reads the body. Additive: it accepts only text refused before.
  
  Under `lf`, a `payload:` node imported from another movement file (`import { Payment } from "types"`) now gates deliveries the way one declared in the same file does; before, such a listen took any body.
- 712da02: The checker compares every value handed to a plugin with the type the plugin declares for it, by position, in a settings record and in a `through` stage alike. A plain value of another type (`fetchUrl(5)`, `jev.score(x, 5)`, a text where a list is taken), which passed silently, is now a `MOV_CALL_ARG_TYPE` warning. It stays a warning for every 0.12 pin, since those releases admitted it and a plugin may have coerced it; refusing it waits for the next compatibility key (0.13). A text written in place against a plugin's option set is judged as that option: one naming no option is refused with `MOV_ENUM_UNKNOWN_VALUE`, as it already is for a function's parameter.
- ae2629b: A plugin's plain value reaches the program in the type the plugin declares: a number as a number, a boolean as a boolean, a list as a list, answered under `data.value` (a text output may still answer its text). Before, every value but a file arrived as text. A text that spells a declared number or boolean (`"0.8"`, `"true"`) is read as one. Any other value outside the declared type is bound as the 0.12 releases bound it (its text, or a file output's `data.value`) and the run carries a `MOVENG_PLUGIN_WARNING` naming the plugin and what it handed back; failing the call waits for the next compatibility key (0.13).
- 72546f6: `lf` says when a polled listen's first poll sets its mark and fires nothing, as Gmail's does: `gmail: inbox:invoice armed; it fires on changes from now` (under `lf serve` and `lf drain` as an `lf:` line). Before, nothing was printed until the first run, so a live listen looked like a dead one.
- 26c08cc: `lf runs show --json` says when a run finished (`finishedAt`, beside `startedAt`; `null` while it runs or is parked) and lists its writes (`writeRecords`): each one's target (adapter, record type, record id), action (`create`, `update`, `delete`, `link`, …), whether it was committed, and the values it set, capped at 2 KiB each and the first 100 writes. `lf runs --json` shows `finishedAt` too. A run's `writes` now counts every entry into it: after a resume it was only the resumed entry's. The human output still prints counts. A store module may answer `finishedAt` on a run row; it is optional, as is `writeRecords` in a run's outcome.
- c55a2b1: A run's trace names how each model call was asked: an extraction's entry and an `ai()` call's entry carry the `tier` written (`null` for none), the `model` and its `effort`. The tiers share one model and differ in effort, so `quick` and `careful` looked identical in a trace. The TypeScript shim reads both members, and still reads an entry from an artifact that names neither.
- f2ebc20: A write to the movement's event parameter (`write company { … }` in `function onboard(company: <crm-[:Company]->>)`) updates the record the event fired on, through the module's `updateRecord`, as a write to a traversal alias does; `delete company` deletes it. It checked clean before but failed every run (`MOVENG_RUNTIME: 'company' is the movement parameter (the event position) …`), under `lf` and the embedded host alike. The event must name its record (an id and an event type the module lists), else the run says it has no stable record to update.

## 0.12.9

### Patch Changes

- 510d923: `lf connect` sets up an OAuth app only when it is needed: a module whose users may also sign in otherwise (a token: `@lf/attio`'s `attio_token`, `@lf/mcp`'s `mcp_token`) is asked whether to (no by default), and `--yes` sets none up unless `--oauth-authorize-url`/`--oauth-token-url` are given. Adding that module's OAuth credential without an app is refused, naming how to set one up.
- 783f329: `lf` describes an adapter once per connection: each credential bound to the module that the movement files import is asked `listEntryPoints` and `describe` as itself (one bound but never imported is not asked), and each connection is typed by its own answer, as the hosted product types it. Before, every connection of a module was typed by the first credential's answer, so a call another connection's schema allowed could pass `lf check`.
- f15adc8: Under `lf`, two connections of one module (`a = connect attio using AttioA`, `b = connect attio using AttioB`) no longer share inbound events. A delivery to a connection's door (`/api/public/webhook-sync/<provider>/<credential>`, `/hooks/<external>/<credential>`) runs only the listens whose construction names that credential, and listens whose construction names none. A delivery to the module's own install still reaches every listen. `lf serve` registers a webhook per connection, as that connection's credential, for that connection's listens' events; a credential no listen uses has its webhook removed. A polled listen polls as its own connection's credential. A queued event row from before this release reaches every listen, as it did.

## 0.12.8

### Patch Changes

- 7cd7476: Adapter protocol 2.3: a polled source labels each event with its kind (`eventType`), as a pushed event is, and `lf` narrows a polled listen's `events` by it. A poll event with no label (a module older than 2.3) still reaches the listen that polled it, and `lf` says so once per module per process. `PROTOCOL_MINOR` is 3; 2.3 is a rule for sources and a host behaviour, so no module states it. A poll's `movementId` is the listen's pipeline, `listen:<file>:<movement>`. `LF_SECRET__<ENTRY>__MODULE=<module>` makes an entry from the environment that module's install, as `module:` does in the secrets file.

## 0.12.7

### Patch Changes

- 7b8a778: A hop whose WHERE pins a type's discriminant with a literal (`` `listName` == "Master Deals List" `` on an Affinity record's `List Entries`) lands on the member that value picks, taken from the write shape's `discriminated` variants the catalog already carries. The checker types the hop's body and the WHERE's other conjuncts by that member, and the engine drops a landed record of another member before reading its fields. A host's own narrowing (`refinements` / `selectedMembers`) answers first, as before.
- 216a7a4: A module served by `serve-module` keeps a run's read memo and call ceiling, as it does in process. Each call is answered inside the run scope its `cacheScopeId` names: the calls of one run share it, two runs never do, and a call under `<none>` or `<slot>` (a host's own reads, a slot's calls) is answered outside any run.
  
  - The protocol has no message that says a run has ended. A scope is let go after 10 minutes with no call, or when the process keeps 64 and another run arrives (the least recently used goes).
  - The run scope (the read memo and the call ceiling) moved from the engine to `@listen-fire/module-runtime`, which the kit and the engine both stand on. The engine's segment opens it around every in-process adapter call as before; its exports are unchanged.
  - Under `lf`, the Affinity module's `AFFINITY_MAX_CALLS_PER_RUN` now counts, per adapter instance per run segment, as it does in process.
  - `serve-module` says so on stderr, once at start, when the process holds more than one copy of `module-runtime`'s run scope: a module on a different copy than the kit's would silently have no run cache or call ceiling.
